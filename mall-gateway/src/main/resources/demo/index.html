示例商城演示控制台

mall-evolution 的演示页，只用于演示：由网关在 demo profile 下托管，生产不启用。所有请求都经网关 /api/** 发出，下面每张卡片展示一个设计点的原始请求与响应。

登录状态：未登录 接口返回的 X-Trace-Id（成功）或 ProblemDetail 的 traceId（失败）显示在每条记录末尾。

a登录

演示账号 13800000000 / mall123 换取 JWT 访问令牌，只保存在本页内存里，刷新页面即丢失；网关和下游服务各自校验同一个令牌。
对应文章：接口设计 · 鉴权

b商品详情两级缓存

响应头 X-Cache 标出这次命中哪一层：热门商品启动时已预热进 Redis，首查命中 L2；其余商品（如已下架的 20004、不存在的 99999）首查回源 DB 并写入 Redis；30 秒内再查命中本地 L1（Caffeine）。
对应文章：引入缓存 · 商品详情两级缓存

c幂等下单

客户端为每次「提交订单」生成一个 Idempotency-Key；同一个 Key 重放时不会重复下单，返回同一个订单号并带 Idempotent-Replayed: true。
对应文章：接口设计 · 下单幂等
同一商品待支付最多 2 单（下单频控）；演示环境 1 分钟不支付自动关单，稍等即可再下。

d模拟支付回调

下单 → 创建支付单 → 以「模拟渠道」身份带 HMAC 签名回调；支付服务发 payment-succeeded 消息，订单异步变为待发货，再经 order-paid 消息给用户加积分。
对应文章：跨服务一致性 · 支付成功
签名密钥是本地开发占位值 dev-only-mock-pay-secret，与 dev / demo profile 一致；真实渠道由对方 SDK 验签。

e超时关单

下单时写一条 order-timeout 定时消息（演示环境 1 分钟，生产 15 分钟）；到点未支付即关单，并经 order-cancelled 消息把预占的库存还回去。
对应文章：异步化 · 超时关单

f熔断

给库存服务的 reserve 注入 800ms 延迟（超过订单侧 500ms 读超时）：前几单按「结果未知」失败（500），失败率过半后熔断打开，后续请求不再发出，直接返回 503 SYSTEM_BUSY 并带 Retry-After。
对应文章：稳定性 · 超时、熔断与舱壁
演示环境：最近 6 次调用里 3 次起算、失败率 ≥ 50% 打开，15 秒后半开放 2 个探测请求。下单路由网关限流每用户每秒 1 次，所以间隔 1.2 秒发送。

g链路 ID

每个服务都挂了 OpenTelemetry Java Agent（演示环境不导出数据），网关生成的 traceId 经 traceparent 传到下游、并穿过本地消息表；同一次请求在各服务日志里用它串起来。
对应文章：可观测与发布 · 三类信号怎么串起来

# 高可用、高并发与高性能实验

给 Java Doc「高可用」「高并发」「高性能」三个模块的实验型实战文章准备的实验方案、脚本与参数。每个实验都按同一个套路做：**现象 → 用 mall-evolution 复现 → 看指标定位 → 加上手段再压一次 → 前后数据对比 → 链回原理篇**。文章里的每个数字都要从这里跑出来，不估算、不编造；跑之前的「预期」只是假设，以实测为准。

三个系列共用同一套脚本与约定：高可用系列是 A–D，高并发系列是 E–H，高性能系列是 I–L；各自的结论见第九节。高性能系列不注入故障也不加量，看的是一次请求本身的时间和 CPU 花在哪，约定见「高性能系列的公共约定」。

| 实验 | 现象 | 对照组 → 实验组 | 单轮时长 | 对应原理篇 |
|------|------|----------------|---------|-----------|
| [A 下游变慢](#实验-a下游变慢超时舱壁熔断各挡住什么) | 库存服务 reserve 变慢 5 秒，下单卡死，连不依赖库存的商品详情也跟着超时 | 无保护 → 超时 → 舱壁 → 熔断（→ 连接池） | 约 8 分钟 | 超时重试与隔离、熔断 |
| [B 重试风暴](#实验-b重试风暴与幂等) | 支付查询抖了 20 秒，故障结束后系统却恢复不过来；超时重试下出重复订单 | 不受控重试 → 退避 + 抖动 + 预算 + 熔断；换键重试 → 同键重试 | B1 约 7 分钟，B2 约 3 分钟 | 超时重试与隔离、熔断 |
| [C 滚动发布](#实验-c滚动发布丢不丢请求) | 持续压测中逐个重启 3 个 mall-app，每次重启都有一串 5xx | 裸停 → 优雅停机 → 先注销再停 →（缩短网关实例缓存） | 约 12 分钟 | 优雅上下线与变更、冗余与故障转移 |

| [F 多级缓存](#实验-f多级缓存每一层挡住了什么击穿与穿透) | 详情页每个请求都查库，浏览量一高数据库先顶不住；热点商品的缓存一过期，一批请求同时回源；不存在的商品每次都查库 | 没有缓存 → 只有 Redis → 本机 + Redis；不单飞 → 单飞；不缓存空值 → 缓存空值 | F1 约 10 分钟，F2、F3 约 5 分钟 | 高并发：缓存架构 |
| [G 异步削峰](#实验-g异步削峰高峰留在消息队列里) | 下单量突然翻三倍，下单接口没事，但消费慢的那一环越积越多，高峰过了很久才消化完 | 消费不慢 → 每条 100ms、2 / 4 / 8 个消费线程 | 约 12 分钟 | 高并发：削峰 |
| [H 连接池与线程池、实例数](#实验-h连接池与线程池实例数) | 「连接池调大就快了」「机器加一倍就能扛一倍流量」——都不一定 | 连接池 5 → 10 → 20 → 40 → 80；Tomcat 线程 50 / 200 / 400；mall-app 1 → 2 → 3 个实例 | 约 8 分钟 | 高并发：水平扩展、数据层扩展、容量规划 |
| [I 定位](#实验-i定位一次请求的时间花在哪) | 负载很轻，订单列表却要几十毫秒；语句统计里近一半不是业务语句；网关每个请求都在翻配置 | 不加索引提示 → 加；驱动默认连接属性 → 记住会话状态；每次查端口 → 查一次记住；另有一个「改了也量不出来」的对照 | 约 7 分钟 | 高性能：方法论、分析工具、端到端案例 |
| [J 数据访问](#实验-j数据访问sql-的几种写法各差多少) | 翻到后面的页越来越慢；一页订单发了二十多条 SQL；批量导入每秒只有一两千行 | 偏移量 → 延迟关联 → 游标；逐单查明细 → 一次 IN / JOIN；逐条 → 一条语句多行 / JDBC 批量（驱动改写与否） | 4–7 分钟 | 高性能：数据访问性能、异步与批量 |
| [K JVM](#实验-kjvm收集器堆大小预热) | 「换个收集器就快了」「刚发布的实例总是慢」 | G1 / ZGC / Parallel / Serial × 堆 1GB / 512MB；JDK 21 → 25；预热 → 不预热 → 慢启动 | 约 6.5 分钟 | 高性能：JVM 层性能策略 |
| [L 微基准](#实验-l微基准用-jmh-量几段纯-cpu-逻辑) | 手写计时循环量出来的数不可信；微基准里快几倍的写法，放回接口里看不出来 | 现在的写法 → 对照写法，JMH 量单次耗时与分配 | 约 8 分钟 | 高性能：基准测试、代码级优化 |

### 先说一个已经确认的问题：服务间调用只有 5 条连接

不用跑压测就能确认（`mall-common` 的 `HttpClientPoolConfigTest` 把它写成了测试）：

- `RestClient` 的底层是 Apache HttpClient 5——它是随 `nacos-client` 间接引进来的，Spring Boot 检测到它就优先用它
- Spring Boot 不改 HttpClient 5 的连接池：**每个目标地址（下游一个实例）最多 5 条连接、总共 25 条**，取连接的等待上限 **3 分钟**
- `spring.http.serviceclient.*.read-timeout` 管的是拿到连接之后的读超时，**管不到排队等连接这一段**
- 舱壁许可（下单 60、详情库存查询 20）都大于 5，挡不住「60 个线程排队等 5 条连接」

这意味着：下游一变慢，5 条连接很快被占满，后面的调用在池子里一等就是几分钟；详情页的库存提示和下单共用这个池子（同一个下游地址），也会被拖住。实验 A 实测了它的影响（A3 → A4），随后三个服务的 `application.yml` 都把连接池放开到每个下游实例 100 条、取连接最多等 100ms；A0–A4 的参数文件把修复前的值钉住，仍然可以复现。见「九、实验结论与随后的修改」。

## 二、环境与拓扑

| 位置 | 跑什么 |
|------|-------|
| 开发虚拟机（共用） | MySQL、Redis、Nacos、RocketMQ（`docker compose up -d` 那套）；监控 Prometheus（9091）、Grafana（3001），compose 项目 `mall-monitoring` |

|------|---------|---------|------|
| mall-app | 8080（C 另有 8180、8280） | 18080（18180、18280） | 雪花机器号 1、2、3 |
| inventory-service | 8082 | 18082 | |
| payment-service | 8083 | 18083 | |

几点约定：

- **本机资源**：每个服务最大堆 1GB，A / B / D / E / F / G 起 4 个 JVM、C 起 6 个、H 起 4–6 个，加上 Maven 与 Gatling 的 JVM，建议空闲内存 8GB 以上；压测期间本机不要跑别的重活
- **实验用的 MySQL**：`innodb_flush_log_at_trx_commit=2`、`sync_binlog=0`（事务提交时不逐次刷盘，日志大约每秒刷一次）。原因：每次提交都刷盘时，每秒几百次提交会让虚拟机的虚拟磁盘一卡就是几秒，高并发系列的试跑多次被它打断（见「八、局限」）。这是实验环境的设置，不是对正式环境的建议——它用「宕机可能丢最后约 1 秒的事务」换写入吞吐

- **profile**：`dev,local,demo`，工作目录是仓库根目录，中间件地址来自 `config/application-local.yml`（不进仓库）。demo 的演示节奏里，下单熔断「3 次就起算」由 `common.properties` 拨回正式参数；「1 分钟未支付关单」保留（它会把实验订单占的库存及时还回去）
- **参数优先级**：实验参数全部以命令行参数 `--key=value` 传给服务，优先级最高，共用 Nacos 里有同名配置也盖不住。实验 A、B、C、D 各自把要对照的正式值也显式写了一遍
- **实验用户**：用 dev 环境的本地占位 JWT 密钥（`application-dev.yml` 里那串）直接签访问令牌，用户 ID 从 900000001 起（B2 按时间另取一段），不在 `t_user` 里。原因：演示账号只有 8 个，而网关下单限流是每人每秒 1 次、订单服务有「同一 SKU 待支付最多 2 单」的频控，几个账号压不出几十单每秒。只调下单、查订单、查支付状态这些只认令牌里用户 ID 的接口，不调「我的」。E、H 一轮要用十几万到几十万个用户，不预签也不循环：从 10 亿起按当前时间取一段（每过 1 秒起点往后挪 1 万个），每个请求依次往后取一个，一轮之内、相邻两轮之间都不重复
- **库存**：每轮开始前把 20001–20003 补到 10 万（只补不减），实验订单 1 分钟后被超时关单、库存归还。E 只补热点 SKU（20001）、H 补三个 SKU，都补到 30 万——单数太多，不指望关单及时把库存还回来；这两个实验收尾时会等实验订单关完（库存回到压测前的数）再停服务，免得积压的关单带进下一轮
- **数据量**：A 一轮最多约 1.4 万单、C 约 6000 单、D 约 7000 单，全是待支付后被关单的订单，加上本地消息与预占记录，MySQL 每轮多几万行。E 默认的阶梯一轮 20.31 万单（都成功的话）；H 一轮的单数由吞吐决定（试跑见实验 H）。这两个实验每轮给 MySQL 多写一两百万行，跑之前确认开发虚拟机的磁盘够用。F 只读商品、不下单，不往 MySQL 写东西（`f3-penetration-random-on` 一轮会往 Redis 写约 3.6 万个 60 秒过期的空值占位）；G 一轮约 1 万单
- **Nacos 命名空间**：共用 Nacos 时，别人的 mall-app 实例会被网关当成自己的。建议给实验单独建一个命名空间，跑脚本时加 `-NacosNamespace <命名空间 ID>`

## 五、各个实验

下面每个实验都写明：假设、前置条件、拓扑、压测、注入或动作、对照组与实验组的差异、看哪些数据、预期、判定、截图。**「预期」是跑之前的假设**，文章以实测为准，和预期不符的地方恰恰值得写。

### 实验 A：下游变慢——超时、舱壁、熔断各挡住什么

- **假设**：库存服务变慢时，没有保护的 mall-app 会被拖垮，而且拖垮的不只是下单——商品详情不依赖 reserve，但它和下单共用 Tomcat 线程池和到库存服务的 HTTP 连接池，也会跟着超时。超时、舱壁、熔断每加一层，能看到一个具体的改善
- **前置条件**：开发虚拟机中间件可用；本机没有别的服务占端口
- **拓扑**：mall-app ×1、库存 ×1、支付 ×1、网关 ×1
- **压测**（`SlowDownstreamSimulation`）：开放模型，下单 40 单/秒 + 商品详情 100 次/秒，共 6 分钟，客户端超时 10 秒
- **注入**：第 60 秒给库存服务的 `POST /internal/inventory/reserve` 加 5000ms 延迟（规则 `a-reserve-slow`），持续 180 秒后撤销，再观察 2 分钟恢复
- **抓线程栈**：第 90、150 秒，mall-app 与库存服务各一份

| 变体 | 读超时（mall-app → 库存） | 网关超时 | 舱壁 | 熔断 | 连接池 |
|------|------|------|------|------|------|
| `a0-no-protection` | 60 秒 | 60 秒 | 10000（等于没有） | 关（最少 1 亿次才统计） | 默认（5 条 / 3 分钟） |
| `a1-timeout` | **500ms** | **3 秒** | 10000 | 关 | 默认 |
| `a2-bulkhead` | 500ms | 3 秒 | **60** | 关 | 默认 |
| `a3-circuit-breaker`（正式配置） | 500ms | 3 秒 | 60 | **开**（10 秒窗口、至少 100 次、失败率或慢调用率 ≥ 50% / 60%，打开 5 秒） | 默认 |
| `a4-pool`（视 A3 结果） | 500ms | 3 秒 | 60 | 开 | **每目标 100 条、取连接最多等 100ms** |
| `a3b-ignore-bulkhead`（验证修复） | 500ms | 3 秒 | 60 | 开，**忽略舱壁满的异常** | 默认 |
| `a5-fixed`（修复后的正式配置） | 500ms | 3 秒 | 60 | 开，忽略舱壁满的异常 | 每目标 100 条、取连接最多等 100ms |

A0–A4 的「默认连接池」「熔断器不忽略舱壁异常」是修复前的值，钉在 `common.properties` 里。

- **看哪些数据**：
  - 压测：`timeline.csv` 里「POST /api/orders」「GET /api/products/{skuId}」逐秒的状态码分布和 P99；Gatling 报告两个请求的 OK 比例、P99
  - mall-app：Tomcat 忙线程（`tomcat_threads_busy_threads`）、到库存的客户端调用耗时（`http_client_requests_seconds_max{uri=/internal/inventory/reserve}`）与库存服务端耗时之差（= 排队等连接的时间）、舱壁剩余许可、熔断状态与拒绝数
  - 线程栈分类：等连接池 / 等下游响应 / 等本机缓存加载 各多少
  - 面板 `mall-ha-experiments` 的「mall-app」「服务间调用的保护」两行
- **预期**：
  - A0：注入后几秒内 Tomcat 忙线程顶到 200，下单与详情都大面积超时；撤销后要等排队的请求慢慢消化才恢复
  - A1：读超时 500ms 让单次调用不再等 5 秒，但如果线程栈显示大量线程在「等连接池」，说明超时管不到这一段，改善有限
  - A2：舱壁把同时调库存的线程压在 60 个，Tomcat 还有余量，下单多出来的部分立刻返回 503 `SYSTEM_BUSY`；详情页是否恢复，取决于它的库存查询是否也卡在同一个连接池上
  - A3：熔断打开后下单在本进程内直接失败（毫秒级），库存服务收到的 reserve 降到半开探测的量；撤销后 5 秒内半开、恢复
  - A4：如果 A3 里详情页仍受影响，连接池开关应当让它和注入前一样
- **判定**：每组算三个数——注入期间详情页成功率与 P99、下单失败的平均耗时（失败得快不快）、撤销后多少秒恢复到注入前的 P99 两倍以内。以 A0 为基线对比
- **截图**：每组一张面板截图（「mall-app」与「服务间调用的保护」两行，时间范围覆盖注入前 30 秒到撤销后 60 秒）；A0、A3 各一张 Gatling 报告的响应时间分布；一份线程栈分类对比表（由 summary.csv 汇总）
- **预计耗时**：每组约 8 分钟（起服务 1 分钟 + 压测 6 分钟 + 收尾），4–5 组约 40 分钟

### 实验 B：重试风暴与幂等

#### B1 重试风暴：同一个 20 秒的小故障，重试策略决定能不能自己恢复

- **假设**：下游容量有限时，不受控的重试（立刻重试、多层叠加、不看 Retry-After、没有预算）会把一次 20 秒的小故障放大成「故障结束后也恢复不了」的亚稳态：排队的积压里大多是调用方早已放弃的请求，下游忙着做白工，新请求继续超时、继续重试。受控的重试（退避 + 抖动 + 预算 + 熔断）让积压在故障结束后很快消化
- **链路**：App 轮询支付状态 `GET /api/orders/{orderNo}/payment` → 网关 → mall-app（`PaymentQueryClient`：重试 + 熔断 + 舱壁）→ 支付服务 `GET /internal/payments/{orderNo}`
- **拓扑**：同 A
- **压测**（`RetryStormSimulation`）：先让 600 个实验用户各下一单（约 12 秒），之后每秒 150 次「首次查询」（不含重试），持续 5 分钟；App 超时 2 秒
- **注入**（规则 `b-pay-capacity`，轮询开始即生效）：支付查询并发上限 10、每个请求占用 40ms（容量约 250 次/秒，平时负载约六成）；轮询第 60 秒起把占用时间改成 400ms（容量掉到约 25 次/秒），持续 20 秒后改回 40ms。排队不设超时，调用方放弃的请求轮到时照样处理
- **两组都放开服务间连接池**（每目标 500 条、取连接最多等 200ms），免得 HttpClient 默认的 5 条连接先成为瓶颈

| 变体 | App 重试 | mall-app 重试 | 熔断 / 舱壁（payment-query） |
|------|---------|---------------|---------------------------|
| `b1-naive` | 立刻重试，最多 3 次，不看 Retry-After，不设预算 | 立刻重试 3 次 | 关 / 10000 |
| `b1-controlled` | 指数退避 + 全抖动（200ms 起、封顶 2 秒），遵守 Retry-After，预算 10% | 正式配置：重试 1 次、退避 20–80ms | 开（10 秒窗口、至少 50 次、失败率 50%，打开 10 秒）/ 20 |
| `b1-client-only`（可选） | 同 controlled | 同 naive | 同 naive |
| `b1-server-only`（可选） | 同 naive | 同 controlled | 同 controlled |

- **看哪些数据**：
  - 放大倍数：Gatling 里「(重试)」请求数 / 首次请求数（App 层）；支付服务收到的请求 / mall-app 收到的请求（服务端层，面板「支付查询放大倍数」）；两者相乘是总放大
  - 积压：`demo_fault_waiting{rule="b-pay-capacity"}`（瓶颈前排队数）、支付服务 Tomcat 忙线程
  - 恢复时间：小故障结束后，首次查询的成功率回到 95% 以上并保持 10 秒的那一刻，减去结束时刻
  - 重试计数：`remote_retryable_failures_total`、`remote_retryable_exhausted_total`；熔断拒绝数
  - 压测结束时日志里的「客户端重试预算」统计（首次请求数、放行与拒绝的重试数）
- **预期**：naive 组小故障期间排队数一路上涨、结束后不回落，成功率在压测剩下的时间里都起不来；controlled 组排队有限，故障结束后十几秒内恢复。两个可选组用来分清 App 端和服务端各贡献了多少
- **判定**：恢复时间（naive 可能是「压测结束前没恢复」）、故障期间与之后的总放大倍数、排队峰值
- **截图**：两组的「支付查询放大倍数」「注入的故障：排队与在途」面板；`timeline.csv` 画出的首次查询成功率曲线（两组叠在一张图上，标出故障开始与结束）
- **预计耗时**：每组约 7 分钟，2–4 组约 15–30 分钟

#### B2 超时重试必须配幂等

- **假设**：服务端已经下单成功、但响应迟到导致 App 超时，App 重试时如果换了新的 `Idempotency-Key`，就会重复下单；整个下单意图沿用同一个键，重试只会拿到第一次的结果
- **压测**（`RetryIdempotencySimulation`）：每秒 5 个新用户各有一次下单意图，持续 60 秒；App 超时 1.5 秒，超时立刻重试最多 3 次；结束后等 5 秒，查每个用户的订单列表数一共生成了几单
- **注入**（规则 `b2-order-late`，mall-app）：30% 的下单请求在业务处理完、订单已写库之后，响应再晚 2500ms 才发出

| 变体 | 重试时的 Idempotency-Key |
|------|------------------------|
| `b2-new-key` | 每次重试换新的 |
| `b2-same-key` | 整个意图同一个 |

- **看哪些数据**：`intents.csv`（「生成了几单、App 最后看到的状态码」→ 用户数），Gatling 里「POST /api/orders (重试)」的数量，响应头 `Idempotent-Replayed`
- **预期**：new-key 组约三成的意图生成 2 单（订单服务「同一 SKU 待支付最多 2 单」的频控把重复单封顶在 2，第 3 次重试会收到 409），same-key 组全部是 1 单
- **判定**：重复下单的意图占比
- **截图**：两组 `intents.csv` 的对比表即可
- **预计耗时**：每组约 3 分钟

### 实验 C：滚动发布丢不丢请求

- **假设**：逐个重启实例时，丢请求来自三处——在途请求被掐断（没有优雅停机）、实例还在注册中心里就已经不接请求（停之前没注销）、调用方的实例列表缓存还没过期（网关 LoadBalancer 默认缓存 35 秒）。优雅停机只解决第一处；先注销再停解决第二处；第三处要看缓存过期时间与注销后等待时间谁长
- **拓扑**：mall-app ×3（8080 / 8180 / 8280）、库存 ×1、支付 ×1、网关 ×1
- **压测**（`RollingRestartSimulation`）：商品详情 60 次/秒 + 下单 10 单/秒 + 查订单 10 次/秒，共 10 分钟，客户端不重试（要看发布本身丢了什么），超时 5 秒
- **注入**：第 60 秒起逐个重启三个实例，两次之间隔 60 秒；每一步写进 `script-events.csv`

| 变体 | 停 | 起 | 网关实例缓存 |
|------|----|----|------------|
| `c0-hard` | SIGTERM + `server.shutdown=immediate`，不先注销 | Web 服务器一起就注册 Nacos（不等就绪）；端口一监听就重启下一个 | 35 秒 |
| `c1-graceful` | SIGTERM + 优雅停机（正式配置），不先注销 | 就绪后才注册（正式配置）；等就绪 | 35 秒 |
| `c2-offline-first` | 先 `/internal/offline` 注销，等 15 秒，再 SIGTERM（同 k8s preStop） | 同 C1 | 35 秒 |
| `c3-short-lb-cache`（视 C2 结果） | 同 C2 | 同 C1 | **5 秒** |
| `c3b-longer-wait`（可选） | 注销后等 **40 秒** | 同 C1 | 35 秒 |
| `c4-crash`（可选，故障演练） | kill -9，5 秒后拉起 | 同 C1 | 35 秒 |
| `c5-fixed`（修复后的正式配置） | SIGTERM；停机一开始主动注销，等 10 秒后优雅停机，消费者并行关闭 | 同 C1 | **5 秒** |

- **看哪些数据**：
  - 每次重启丢了几个请求：`timeline.csv` 里非 2xx / 409 的请求（含状态 0），按 `script-events.csv` 的时间切成三段统计
  - 丢在哪一步：失败集中在「SIGTERM 到进程退出」之间（在途被掐断），还是「进程退出之后」（网关还往已经没了的实例上发，网关返回 5xx）
  - **Nacos 下线时序**（C2 起）：从「注销」那一刻起，这个实例的请求计数（`metrics.csv` 里该实例的 `http_server_requests_seconds_count`）还涨了多少秒——即网关还在往它身上发请求的时长
  - 面板「实例（滚动发布）」两行：各实例每秒请求、抓取状态；网关 5xx
- **预期**：C0 每次重启都有一串 5xx；C1 在途请求不再被掐断，但进程退出后到网关缓存过期前仍有失败；C2 若「注销后还收到请求的时长」超过 15 秒，说明 15 秒的等待不够，仍会丢少量请求——这时跑 C3（或 C3b）确认缩短缓存（或加长等待）后能做到零失败
- **判定**：每次重启的失败数（三次取平均）、注销后还收到请求的时长；零失败为通过
- **截图**：每组「各 mall-app 实例每秒请求」面板（能看到三个实例轮流掉到 0 再回来）叠加网关 5xx；C2 的「注销 → 最后一个请求」时间线（由 `metrics.csv` 画）
- **预计耗时**：每组约 12 分钟，4 组约 50 分钟

### 实验 D：突发流量与过载保护

- **假设**：流量超过容量时，不限流的结果是所有请求一起变慢、一起超时——包括核心的下单。在入口把超出容量的非核心流量（匿名浏览）拒掉，下单就能保持正常；降级只在被降的那部分真的是瓶颈时才有用
- **拓扑**：同 A
- **容量模型**（默认打开）：给 mall-app 的全部 `/api/**` 请求注入统一的处理能力上限（规则 `d-app-capacity`：并发 10、每个请求占用 20ms，约 500 次/秒），下单和浏览共用。这样拐点不受本机 CPU 和压测自身开销影响，换台机器也能复现；文章里要写明这是模型。想测本机真实容量用 `d0-probe-real`
- **压测**（`OverloadSimulation`）：下单始终 20 单/秒；匿名浏览 = 商品详情 70% + 猜你喜欢 30%，都走网关的 `anonymous` 路由（没有用户身份，按用户限流挡不住）；客户端超时 3 秒
  - D0（`d0-probe`）：浏览量从 100/s 起每分钟加 100，加到 800/s，找下单 P99 超过 800ms 或开始出错的拐点
  - D1–D4（burst）：平时浏览 150/s，第 60 秒起升到 900/s（约容量的 1.8 倍）持续 180 秒，再回落

| 变体 | 网关 anonymous 路由限流 | 降级（猜你喜欢改固定列表） |
|------|------------------------|--------------------------|
| `d1-none` | 无 | 无 |
| `d2-limit` | **240/s，突发 240**（压满后实测处理量约 316/s 的四分之三；贴着容量的 300/s 用 `-Set` 跑） | 无 |
| `d3-degrade`（可选） | 无 | 高峰开始 30 秒后打开 |
| `d4-limit-degrade` | 240/s | 高峰开始 30 秒后打开 |

- **看哪些数据**：下单的成功率与 P99（高峰前、高峰中、高峰后三段）；网关 429 与 `gateway_route_limited_total`；容量模型的排队数 `demo_fault_waiting{rule="d-app-capacity"}`；mall-app Tomcat 忙线程；浏览请求的成功率（被限流的部分算拒绝，不算故障）

- **判定**：高峰期间下单成功率与 P99；被限流拒绝的浏览请求占比
- **截图**：D1、D2 的「网关每秒请求（按状态码）」「P99 耗时」「注入的故障：排队与在途」面板；D0 的阶梯曲线（浏览量 vs 下单 P99）
- **预计耗时**：D0 约 10 分钟，其余每组约 8 分钟，共约 40 分钟

### 实验 E：热点库存——单行扣减与分桶

- **假设**：所有人下单同一个 SKU 时，库存服务的每次预占都要更新 `t_inventory` 的同一行，行锁从 UPDATE 一直持有到事务提交，预占只能一个一个过；每秒成功单数涨到「1 秒 ÷ 一次持锁的时间」附近就不再涨，再加压只是多出失败。把这一行拆成 N 个桶（`t_inventory_bucket` 的 N 行，预占按订单号哈希落到其中一行），拐点随 N 上移，直到别的瓶颈先到
- **持锁时间模型**（默认打开）：库存服务带 `mall.demo.reserve-hold-ms=10`——预占扣完库存之后，事务提交之前多停留 10ms，这 10ms 里行锁一直占着。于是一行每秒大约只能过 1000 ÷ 10 = 100 单，拆成 n 个桶约为 n 倍，拐点不再取决于这台机器的磁盘和 CPU。**这是模型，不是真实耗时**：开发机上一次预占真实的持锁时间很短，单行的拐点压不出来（先到的是别的瓶颈，见下面「试跑的数」）；生产上持锁时间由同一事务里的其他语句、提交落盘和网络往返决定。文章里要写明这一点；设成 0 即关掉
- **前置条件**：同 A；热点 SKU 不能还留着上一轮的分桶（脚本开始时会先并回去，并不回去就不跑）
- **拓扑**：同 A（mall-app ×1、库存 ×1、支付 ×1、网关 ×1）
- **压测**（`HotStockSimulation`）：开放模型，只有下单，全部打 SKU 20001；每个请求换一个新的实验用户（网关每人每秒 1 单、订单服务同一 SKU 待支付最多 2 单，用户不能重复）和新的 `Idempotency-Key`；客户端超时 3 秒；只有 201 算成功（库存备足、用户不重复，出现 409 说明前提没满足）
  - 预热 30 秒、20 单/秒，请求名带「(预热)」，不计入各级。服务刚起来时头几秒的请求要几百毫秒到几秒，足以把下单的熔断器打开——第一次试跑没有预热，第一级的成功率只有 48%
  - `stair`（默认）：50 单/秒起，每 90 秒加 50，加到 450 单/秒，共 9 级 13.5 分钟、20.25 万单（加预热 20.31 万）
  - `steady`：固定速率压一段，找到拐点后在拐点两侧各压几分钟，确认能不能长时间稳住：`-Set "experiment:ha.mode=steady","experiment:ha.orderRps=250","experiment:ha.durationSec=300"`
- **动作**（脚本做，不注入故障）：
  - 压测前：把热点 SKU 补到 30 万件并核对不少于这一轮计划的单数（不指望关单及时把库存还回来）；`buckets` 大于 0 时调 `POST /internal/inventory/buckets/20001/split?count=N`——库存服务在一个事务里锁住主行，把可售库存平均分到 N 个桶（除不尽的余数给前几个桶），主行库存清零、`bucket_count` 置为 N。脚本核对库存服务日志里的「SKU 20001 拆成 N 个桶，库存 …」，以及拆完各桶之和等于拆之前的库存，结果写进 `script-events.csv`
  - 压测中：第 255、705 秒（含预热；第 3 级 150 单/秒、第 8 级 400 单/秒的中间）各抓一次 mall-app 与库存服务的线程栈
  - 压测后：合并（`…/merge`）要求各桶没有未释放的预占，否则库存服务拒绝，所以分两步清。第一步，下单失败后 release 也失败的预占（mall-app 日志「释放预占失败，交给过期回查」）本来要等库存服务的过期回查才释放——预占 16 分钟后才过期，回查每 5 分钟一轮、一轮 200 条，积压多时要等很久；脚本从日志里取出这些订单号，替它提前调 `POST /internal/inventory/release`（按订单号幂等）。第二步，等实验订单关完、库存回到压测前的数（最多 30 分钟，连续 2 分钟不再变化就不等了）。然后合并
  - 没并回去时脚本最后会明说。下一轮 E 开始时会先并一次，不行就按最近 3 轮的 mall-app 日志补做上面的释放再反复尝试（最多等 30 分钟）；手工处理：服务起着的时候 `Invoke-WebRequest -Method Post http://localhost:8082/internal/inventory/buckets/20001/merge`，返回 5xx 说明还有预占没释放，过一会儿再试

| 变体 | 桶数 | 预占更新哪一行 |
|------|------|---------------|
| `e0-single-row` | 0（不分桶） | `t_inventory` 里热点 SKU 的那 1 行 |
| `e1-buckets-4` | 4 | `t_inventory_bucket` 的 4 行之一：从 `hash(订单号) % 4` 号桶起，不够再试下一个 |
| `e2-buckets-8` | 8 | 8 行之一 |
| `e3-buckets-16` | 16 | 16 行之一 |

四个变体的服务启动参数完全一样：正式配置（`common.properties` 里显式写了一遍：mall-app 到库存的读超时 500ms、下单舱壁 60、熔断开，库存服务连接池 40（取连接最多等 250ms），mall-app 连接池 20，网关超时 3 秒），外加库存服务的持锁时间模型 `mall.demo.reserve-hold-ms=10`。临时换桶数用 `-Set "script:buckets=32"`，换持锁时间用 `-Set "inventory-service:mall.demo.reserve-hold-ms=5"`。

- **看哪些数据**：
  - 压测：`timeline.csv` 里「POST /api/orders」按 `events.csv` 的「第 N 级」切段，每一级的每秒成功单数、成功率、P99，以及失败的状态码——503 是舱壁满或熔断打开，500 是预占失败（库存服务取不到数据库连接、读超时），504 与 0 是网关或客户端超时
  - 库存服务：reserve 的服务端耗时（`reserve_server_p99`、`reserve_server_avg`，排队等行锁直接体现在这里）、HikariCP 活跃与等待（40 条用满还有人等，说明都卡在同一行上）、Tomcat 忙线程
  - mall-app：舱壁剩余许可、熔断状态与拒绝数、HikariCP 活跃与等待、Tomcat 忙线程；客户端看到的 reserve 耗时与服务端耗时之差
  - 线程栈：库存服务的 Tomcat 线程有多少停在 MySQL 的读上（等行锁）
- **预期**（都是跑之前的假设）：
  - E0：按持锁时间模型，单行每秒大约过 100 单，拐点应当落在第 2 级（100 单/秒）附近；实际每单占锁的时间比 10ms 略长（扣减语句本身、提交），1 分钟后关单时的释放也要更新同一行（见下面最后一条），所以多半略低于 100
  - E1–E3：按模型，4 个桶约 400 单/秒，落在阶梯之内；8 个、16 个桶约 800、1600 单/秒，高于阶梯上限 450——这两组在阶梯内应当看不到行锁造成的拐点，如果看到了，就是别的瓶颈先到（下单舱壁 60、库存服务连接池 40、mall-app 自己每单还要写三张表、本机 CPU；是哪一个，看上面的指标）。想压到它们的拐点用 `-Set "experiment:ha.maxRps=…"` 把阶梯加高。桶数与拐点也不会严格成正比：预占按订单号哈希落桶，各桶的到达并不均匀
  - 过了拐点不是「越来越慢」：reserve 变慢 → 舱壁占满（503）→ 慢调用率过 60% 熔断打开（503，5 秒后半开），每秒成功单数呈锯齿。这些保护手段是正式配置的一部分，本实验不关；想看没有它们时的排队，用 `-Set` 把舱壁放大、熔断关掉另跑一组，并在文章里注明
  - 每一单在 1 分钟后还要释放一次预占（demo 的关单节奏），更新的是同一行或同一组桶：拐点附近，库存行实际承受的是预占加释放两份更新
- **判定**：每一级去掉头 30 秒（换级的过渡），剩下的时间里成功率不低于 99% 且 P99 不超过 800ms 算「撑住」；拐点是最后一个撑住的级。四个变体各得一个拐点和拐点处的每秒成功单数，以 E0 为基线。虚拟机停顿（见「局限」）会造成几秒的全部失败，它和拐点的区别是：低速率的级也会出现、过后完全恢复、库存服务的 40 条连接同时卡住——出现这种情况的轮次重跑，不用它的数
- **截图**：四组的「每秒成功单数 vs 到达速率」阶梯图（由 `timeline.csv` 画，四条线叠在一张图上）；E0 与 E3 在各自拐点后一级的库存服务 HikariCP 活跃 / 等待与 reserve 服务端 P99；E0 的线程栈分类

### 实验 F：多级缓存——每一层挡住了什么，击穿与穿透

- **假设**：商品详情是最热的读接口。没有缓存时每个请求都查一次库，能撑多少取决于数据库和连接池；加上 Redis，查库变成读 Redis，每个请求仍要出一次进程；再加本机缓存，绝大多数请求在内存里命中。三种做法的拐点应当依次上移。缓存也带来两个新问题：热点 key 失效的瞬间一批请求同时回源（击穿），靠单飞挡；请求不存在的 key 每次都落到数据库（穿透），靠缓存空值挡——但空值缓存只对「反复请求同一批 key」有效，对每次都换 key 的请求没用，还白占缓存
- **被测代码**：`mall-product` 的 `ProductDetailService`——L1 本机 Caffeine（写入后 30 秒、最多 1 万条；`local.get(key, 加载函数)` 保证同一个 key 在本 JVM 只有一个线程加载，即单飞）+ L2 Redis（30 分钟 + 0–5 分钟随机）+ 不存在的 SKU 缓存空值（Redis 60 秒，本机同样缓存）。详情页的另一半数据「有货」提示（`StockDisplayService`）有自己的三层缓存，**本实验不动它**：只有 3 个 SKU、本机缓存 2 秒，它每秒最多读一两次 Redis，四个开关都关掉时它也照常缓存
- **前置条件**：同 A；网关没有给 `anonymous` 路由配按路由的总量限流（`mall.gateway.route-limits` 默认一条都不配；共用的 Nacos 里有没有配，脚本收尾时看 `gateway_route_limited_total` 核对，被限流过会在 `script-events.csv` 里明说）
- **拓扑**：同 A（mall-app ×1、库存 ×1、支付 ×1、网关 ×1）
- **压测**（`CacheLayersSimulation`）：开放模型，只有匿名的 `GET /api/products/{skuId}`，走网关的 `anonymous` 路由——这条路由不挂按用户的限流（匿名请求没有用户身份），所以不需要实验用户；客户端超时 3 秒。先预热 30 秒、50 次/秒（请求名带「(预热)」，只请求存在的 SKU）
  - **SKU 只有 3 个**：演示数据（`R__dev_seed_products.sql`）一共 4 个商品，上架的 20001–20003 全部用上，20004 是下架的演示商品、不用。3 个 SKU 谈不上长尾，`stair` 里 80% 的请求给 20001（`ha.hotShare`），其余两个各 10%。键空间这么小，本机缓存和 Redis 的命中率都接近 100%——这个实验比的是「每个请求要不要出进程、要不要查库」，**不是缓存容量、淘汰策略和命中率**，文章里要写明
  - `stair`（F1）：200 次/秒起，每 60 秒加 200，加到 1600 次/秒，共 8 级 8 分钟
  - `breakdown`（F2，击穿）：300 次/秒全部打 20001，持续 180 秒；每 20 秒让它的两级缓存失效一次，共 8 次
  - `penetration`（F3，穿透）：200 次/秒全部打不存在的 SKU，持续 180 秒，期望 404（请求名带「(不存在)」，404 记为 OK）。`ha.missIds=repeat` 在 100 个固定 ID 里循环，`random` 每个请求一个新的随机 ID。ID 都是正整数（9 万亿起），过得了接口的格式校验（`@Positive`）
- **动作**：
  - 缓存开关是 mall-app 的启动参数（只在 demo profile 下生效，默认值与正式环境相同）：`mall.demo.detail-cache.l1-enabled`（false：不用本机缓存）、`l2-enabled`（false：不读也不写 Redis）、`single-flight-enabled`（false：本机未命中时先查一下有没有，没有就各自加载、各自回填，不加锁）、`null-cache-enabled`（false：不存在的 SKU 两层都不缓存）
  - **回源耗时模型**（只有 F2 用）：`mall.demo.detail-cache.load-delay-ms=200`——每次回源先从连接池取一条连接、开事务，停留 200ms，再查库、提交，相当于「回源是一条 200ms 的慢查询」。**这是模型**：演示库里回源只是按主键查一行，一两毫秒就回来，缓存失效的瞬间挤不进几个请求，看不出击穿的代价；真实系统里拼一个详情页要多表关联、调几个下游。按模型，失效后第一个回源回来之前到达的请求约 300 × 0.2 = 60 个，mall-app 的连接池只有 20 条
  - 让缓存失效（F2）：场景每 20 秒调一次运营后台已有的手动清缓存接口 `POST /api/admin/products/20001/cache-evict`（删 Redis 里的 key，再广播让每个实例删本机的；和运营改价后手动刷新是同一条路），没有为实验另加接口。接口要 ADMIN 角色：场景用实验密钥签一个带 ADMIN 角色的令牌，直接调 mall-app 的 8080（不经网关）。返回 204 才在 `events.csv` 记「第 n 次失效」
  - 抓线程栈（F1）：第 240、480 秒（含预热；第 4 级 800 次/秒、第 8 级 1600 次/秒的中间）抓 mall-app 的
  - 收尾：把 mall-app 启动以来的回源总次数、网关有没有按路由限流写进 `script-events.csv`

**F2 的两组为什么都关掉 Redis**：两组只差单飞这一个开关，其余完全相同，对比才干净。关掉 Redis 是为了让「本机缓存失效」和「回源」之间没有别的东西：每次失效后进到加载函数的请求全部查库，`product_detail_db_load_total` 数的就是加载函数被调用的次数。如果只在不单飞的那组关 Redis，两组就差了两个开关，多出来的回源说不清是哪一个造成的。代价是有单飞的那组不再是原样的正式配置（正式配置里 Redis 开着）；想看正式配置下的击穿，用 `-Set "mall-app:mall.demo.detail-cache.l2-enabled=true"` 另跑一组——清缓存接口连 Redis 里的 key 一起删，预期同样是每次失效回源 1 次。另外，单飞只管本 JVM：多个实例时每个实例各回源一次，本实验只有一个 mall-app，看不到这一点。

- **看哪些数据**：
  - 压测：`timeline.csv` 里「GET /api/products/{skuId}」按 `events.csv` 切段（F1 按级，F2 按每次失效前后），每段的每秒成功数、成功率、P99；F3 看「(不存在)」的 404 占比与 P99
  - 回源：`product_detail_db_load_total` 的速率（`metrics.csv` 里相邻两秒相减）。F1 的三组分别应当约等于请求速率、接近 0、接近 0；F2 把每次失效后几秒内的增量加起来，就是「一次失效回源了几次」；F3 看它和请求速率的比
  - 缓存：本机命中率 `cache_gets_total{cache="product_detail",result=hit|miss}`；Redis 的命中、未命中、命中空值 `product_detail_l2_total{result=hit|miss|null}`；F3 另看本机缓存的条数 `cache_size`（随机 ID + 缓存空值时，里面常驻约 200 × 30 = 6000 条只会被读到一次的空值，上限是 1 万条）
  - mall-app：HikariCP 活跃 / 等待、取连接耗时（`hikaricp_connections_acquire_seconds_*`，F2 不单飞时每次失效都应当有几十个请求在等连接）、Tomcat 忙线程、CPU；网关的状态码分布（出现 429 说明被限流，数据不能用）
  - 线程栈（F1）：`f1-no-cache` 的 Tomcat 线程有多少在等数据库连接、多少在数据库上
- **预期**（都是跑之前的假设）：
  - F1：`f1-no-cache` 每个请求一次按主键的查询、连接池 20 条，拐点取决于 MySQL 所在虚拟机一秒能答多少次查询，本机没有测过，可能在 1600 次/秒以内，也可能压完还没到（没到就用 `-Set "experiment:ha.maxRps=…"` 接着压）；`f1-redis-only` 每个请求一次 Redis 往返，拐点高于前者；`f1-two-level` 几乎不出进程，1600 次/秒以内不该有拐点。四个服务和压测机在同一台机器上，高的那几级很可能是本机 CPU 先到——三组的差别主要看同一级上的 P99、CPU 和回源速率，不一定能看到三个清楚的拐点
  - F2：有单飞时每次失效只回源 1 次，这 200ms 里到达的约 60 个请求等同一个结果，P99 约 200ms，连接池只占 1 条；不单飞时约 60 个请求各自回源，20 条连接分三批才轮得完，最后一批要等到约 600ms，HikariCP 等待数冲到几十。按模型，一次失效的回源次数是 1 对 60 左右
  - F3：固定 ID + 缓存空值，每个 ID 60 秒才回源一次（100 个 ID 约每秒 1.7 次），其余在本机或 Redis 里命中空值；固定 ID + 不缓存，每个请求都回源（约 200 次/秒）。随机 ID 时缓存不缓存都是每个请求回源一次——缓存空值不但没用，还每秒往 Redis 写 200 个只会被读到一次的 key（60 秒过期，常驻约 1.2 万个），本机缓存的 1 万条名额里也常驻约 6000 条这样的空值；速率再高一些，就会开始把真正的商品挤出本机缓存。挡这种请求要靠布隆过滤器或入口限流，本仓库没有做
- **判定**：F1 每一级去掉头 15 秒，成功率不低于 99% 且 P99 不超过 200ms 算「撑住」，各组的拐点是最后一个撑住的级，同时列出各级的回源速率；F2 算 8 次失效各自的回源次数（中位数）、失效后 2 秒内的 P99 与取连接等待的峰值；F3 算回源次数 ÷ 请求数
- **截图**：F1 三组的「每秒成功数 / P99 vs 到达速率」阶梯图（由 `timeline.csv` 画，三条线叠在一张图上）与回源速率；F2 两组的「回源次数随时间」（每 20 秒一个尖）与 HikariCP 等待数；F3 四组的回源比例对比表
- **预计耗时**：F1 每组约 10 分钟（起服务 1 分钟、预热与压测 8.5 分钟）；F2、F3 每组约 5 分钟（预热与压测 3.5 分钟）。9 组约 1 小时

试跑里看到、正式跑时要留意的两点：

- 600 次/秒以内，没有缓存的那组和两级缓存的那组耗时看不出差别（数据库按主键查一行很快，20 条连接远没有用满）——差别要到更高的级才可能出现，也可能先碰到本机 CPU
- F2 里除了脚本每 20 秒触发的失效，还多一次**自然过期**：预热时填进本机缓存的那一条 30 秒后过期，正好落在正式阶段开头（`events.csv` 的「击穿开始」之后几秒）。关了 Redis，自然过期同样直接回源，回源次数与强制失效的相当（试跑里有单飞 1 次、不单飞 62 次）。按事件切段时它归在「击穿开始」那一段，统计「一次失效回源几次」时把它算作第 0 次，不要漏掉也不要当成异常

### 实验 G：异步削峰——高峰留在消息队列里

- **假设**：下单接口只做必须同步完成的事（预占库存、写订单、写本地消息），之后的事交给消息。下单量突然翻三倍时，接口的成功率与耗时不变；多出来的后续处理在 Broker 里排队，消费者按自己的处理能力消化。到达速率超过消费能力时，消费延迟一直涨；高峰过后延迟多久回落，取决于消费能力比平时的到达速率多出多少——没有余量就回不来
- **下单之后的消息**（`POST /api/orders` 成功后，按代码走一遍；本实验不支付，所以只走前两行）：

| 何时写进本地消息表 | Topic | 投递 | 消费组 | 所在服务 | 做什么 |
|------|------|------|------|------|------|
| 下单事务内（`PlaceOrderTxService`，mall-app） | `order-timeout` | **定时**：下单后 15 分钟（活动 SKU 5 分钟，demo 环境 1 分钟）才投递 | `order-timeout-consumer` | mall-app | 关单：请支付服务关支付单，订单 10 → 50，写 `order-cancelled` |
| 关单事务内（`OrderCloseService`，mall-app） | `order-cancelled` | 立即 | `inventory-release-consumer` | inventory-service | 释放预占，库存还回去 |
| 支付回调事务内（`PayCallbackService`，payment-service） | `payment-succeeded` | 立即 | `order-payment-consumer` | mall-app | 订单 10 → 20（待发货），写 `order-paid`；订单已关则写 `order-refund-required` |
| 上一行的消费事务内（`OrderPaidTxService`，mall-app） | `order-paid` | 立即 | `notify-consumer`、`shipment-consumer`、`points-consumer` | mall-app | 通知、建发货单、加积分 |
| 同上 | `order-paid` | 立即 | `inventory-confirm-consumer` | inventory-service | 确认预占 |
| 同上（订单已关或重复付款时） | `order-refund-required` | 立即 | `payment-refund-consumer` | payment-service | 原路退款 |

  本地消息都是「事务提交后立刻交给中继发送、每秒扫表兜底」；定时消息也是立刻发给 Broker，由 Broker 到点投递，不在本地消息表里等。所以**下单本身不产生立即消费的消息**：每一单对应的第一条立即消息是 60 秒后关单时发的 `order-cancelled`，由库存服务的 `inventory-release-consumer` 消费——本实验调慢的就是这个消费组。它看到的高峰比下单的高峰晚 60 秒，而且先经过 mall-app 的关单消费组（`order-timeout-consumer`，2 个线程）；关单消费组自己的消费延迟也有记录，可以核对它有没有先把高峰削平
- **前置条件**：同 A；20001–20003 都不在分桶状态；上一轮留在 Broker 里的消息已经消费完（脚本在压测前等消费计数连续 10 秒不变，最多等 3 分钟，等到了多少条会写进 `script-events.csv`）
- **拓扑**：同 A
- **压测**（`AsyncPeakSimulation`）：开放模型，只有下单，在 20001–20003 里随机挑一个 SKU；每个请求换一个新的实验用户和新的 `Idempotency-Key`（理由同实验 E）；客户端超时 3 秒，只有 201 算成功。预热 30 秒、20 单/秒；之后平时 20 单/秒，第 60 秒起升到 60 单/秒、持续 60 秒，再回到 20 单/秒，到第 360 秒为止（升降一步到位），共约 9600 单；压测流量结束后场景再空等 240 秒，逐秒采样一直在记——最后一批订单 60 秒后才关单，积压也要时间消化
  - 时间轴（从压测开始算，含预热）：下单高峰在第 90–150 秒；关单高峰预计在第 150–210 秒到达释放预占的消费组；压测流量在第 390 秒结束，最后一批订单在第 450 秒关单；场景在第 630 秒结束。这几个时刻都记在 `events.csv` 里
- **消费延迟模型**：`mall.demo.consume-delay-ms=100`、`mall.demo.consume-delay-groups=inventory-release-consumer`（库存服务）——这个消费组处理每条消息之前多停留 100ms（停留时不占数据库连接）。**这是模型**：真实的释放预占只要几毫秒，消费能力远高于压得出来的下单量，看不到堆积。**按模型的算术（假设，待实测核对）**：每条 100ms、n 个消费线程，一个消费组每秒大约处理 10 × n 条——2 个线程 20 条/秒，和平时的 20 单/秒刚好相等、没有余量；4 个线程 40 条/秒，低于高峰的 60 单/秒；8 个线程 80 条/秒，高于高峰
- **动作**（脚本做）：压测前等上一轮的消息消费完、补库存；第 180 秒（关单高峰的中间）抓库存服务的线程栈，数出消费线程有几个停在消费延迟上（`threads-*.consume.csv`）；压测后等实验订单关完、库存回到压测前的数再停服务（最多 15 分钟）——没消费完的消息留在 Broker 里，会被下一轮一启动就消费掉

| 变体 | 释放预占的消费组每条消息多停留 | 库存服务每个消费组的线程数 | 按模型的处理能力 |
|------|------|------|------|
| `g0-baseline`（正式配置） | 0 | 8 | 远高于 60 条/秒 |
| `g1-slow-2` | **100ms** | **2** | 约 20 条/秒：等于平时的到达速率 |
| `g2-slow-4` | **100ms** | **4** | 约 40 条/秒：平时有余量，低于高峰 |
| `g3-slow-8` | **100ms** | 8 | 约 80 条/秒：高于高峰 |

其余都是正式配置：mall-app 每个消费组 2 个线程、连接池 20，库存服务连接池 40，网关超时 3 秒。`mall.rocketmq.consumption-threads` 管的是库存服务的两个消费组；另一个（`inventory-confirm-consumer`）在本实验里没有消息。

- **看哪些数据**：
  - 下单接口：`timeline.csv` 里「POST /api/orders」在高峰前、高峰中、高峰后三段的成功率与 P99——四个变体应当没有差别
  - 消费延迟：`mq_consume_delay_seconds_*{group="inventory-release-consumer"}`。`metrics.csv` 里相邻两秒的 `_sum` 之差 ÷ `_count` 之差是这一秒处理完的消息的平均延迟，`_count` 之差是这一秒处理了几条（即实际的消费速率，用来核对「10 × n」）；`_bucket` 之差能算这一秒的 P50 / P99（桶的边界是参数文件里给的 24 个值，25ms–300 秒，分位数只精确到桶；逐秒采样只留了关单与释放预占两个消费组处理成功的桶，全留的话文件太大）；Prometheus 导出里有按 30 秒窗口算好的 `consume_delay_p50` / `p99` / `max`
  - 积压：没有直接的「Broker 里还有多少条」的指标——那要 rocketmq-exporter（`rocketmq_group_diff`），实验环境没有接。用两个数代替：某一时刻的积压 ≈ 到那时为止关单消费组处理完的条数 − 释放消费组处理完的条数（都是 `mq_consume_delay_seconds_count`）；消费延迟本身就是「排到队头用了多久」
  - 本地消息表：`outbox_pending_age_seconds`（最老一条待发送记录等了多久，实验里每秒刷新一次；中继跟得上时是 0 或 1）与 `outbox_failed_count`。它量的是「消息有没有及时发给 Broker」，不是消费得快不快，四个变体应当都贴着 0。表里没有「待发送条数」的指标，想看条数要直接查库（`SELECT COUNT(*) FROM t_outbox WHERE status = 0`）
  - 关单消费组：`mq_consume_delay_seconds_*{group="order-timeout-consumer"}`（定时消息从定好的投递时间算起）——高峰期间它的延迟如果也明显上涨，说明高峰在到达释放消费组之前已经被它削过一次。它的读数在 1 秒以内不可信：定时消息的投递只精确到秒级，Broker 用的又是虚拟机的时钟，试跑里绝大多数读数是 0（按本机时钟，消息在定好的时刻之前就处理完了，负数按 0 记）；它能回答的是「有没有晚几秒」。更直接的核对是它每秒处理的条数有没有跟上下单的高峰。释放消费组不受这个影响——它的消息由本机的 mall-app 发出、本机的库存服务消费，两头是同一个时钟
  - 库存服务：HikariCP 活跃 / 等待、CPU；线程栈里消费线程的分类
- **预期**（都是跑之前的假设）：
  - 下单接口四组一样：成功率 100%，P99 不随高峰变化（60 单/秒远低于实验 E 试跑时撑得住的量）
  - G0：消费延迟在高峰前后都是几十毫秒，看不出高峰
  - G1：消费能力等于平时的到达速率，高峰多出来的约 (60 − 20) × 60 = 2400 条在高峰后一条也消化不掉，延迟涨到约 2400 ÷ 20 = 120 秒后一直停在高位，直到压测流量结束、最后一批订单关完才开始回落
  - G2：高峰期间每秒多积 20 条，到高峰结束积约 1200 条、延迟约 30 秒；之后每秒消化 20 条，约 60 秒回到高峰前的水平
  - G3：消费能力高于高峰，延迟只比 100ms 多一点
  - 实际的处理能力会比 10 × n 略低（每条除了 100ms 还有真正的处理时间），G1 因此可能在平时就缓慢积压；消费者一次从 Broker 取一批消息放在本地等线程处理，等得太久 Broker 会重新投递，延迟很大的那几组可能出现重复消费（消费计数大于订单数）——都要看实测
- **判定**：每组三个数——下单的成功率与 P99（高峰前 / 中 / 后）；释放消费组的消费延迟峰值（逐秒平均值的最大值，以及 P99）；恢复时间，即关单高峰结束（第 210 秒）之后，逐秒平均延迟回到高峰前（第 60–150 秒）中位数的两倍以内并保持 10 秒的那一刻，减去 210 秒（到场景结束都没回来的记「未恢复」）。再用消费速率的实测值核对 10 × n
- **截图**：四组的「释放消费组的消费延迟随时间」叠在一张图上（由 `metrics.csv` 画，标出下单高峰与关单高峰的起止）；同一张时间轴上的下单 P99；G1、G2 的积压估算曲线
- **预计耗时**：每组约 12 分钟——起服务 1 分钟、等上一轮的消息 10 秒以上、预热与压测 6.5 分钟、空等 4 分钟，之后等关单（G1 的积压最多，没有测过要多久）。4 组约 50 分钟

### 实验 H：连接池与线程池、实例数

- **假设**：数据库连接池不是越大越好——太小，请求排队等连接；够用之后再加，吞吐不再涨，多出来的连接只是把排队从连接池挪到 MySQL 里面，P99 反而可能变差。Tomcat 线程数同理：线程比连接多出来的部分，大多在等连接。加实例也不会按比例涨吞吐：mall-app 多了，库存服务、MySQL、网关还是一份
- **前置条件**：同 A；20001–20003 都不在分桶状态（脚本开始时会先并回去，并不回去就不跑）
- **拓扑**：H1、H2 同 A；H3 是 mall-app ×1 / ×2 / ×3（8080、8180、8280），库存 ×1、支付 ×1、网关 ×1
- **压测**（`PoolSizingSimulation`）：**闭环**模型——200 个虚拟用户不加思考时间循环，收到响应立刻发下一个请求，先预热 30 秒（请求名带「(预热)」），再正式压 5 分钟；每一圈 5% 下单（在 20001–20003 里随机挑一个）、95% 查订单列表（`GET /api/orders?size=10`），下单的比例由 `ha.orderWeight` 定（参数文件里是 5；最初是 30，为什么改见「预期」最后一条）；客户端超时 5 秒。闭环下吞吐由被测系统决定，「池子加大以后吞吐变没变」可以直接读出来
  - 虚拟用户与实验用户不是一对一。网关限制每人每秒 1 单，订单服务限制同一 SKU 待支付最多 2 单、而 demo 下 1 分钟后才关单：一个实验用户一分钟最多下 6 单（3 个 SKU 各 2 单），200 个虚拟用户各绑一个实验用户的话，全场最多每秒 20 单，压不出连接池的差别。所以**每一圈换一个新的实验用户**（依次往后取，不重复），一个用户一轮只下一单，两条限制都碰不到
  - 查列表用的是「最近下单成功的用户」里随机挑的一个（记最近 5000 个，攒够 200 个才开始用），查到的是真有订单的列表；攒够之前用这一圈的新用户，查到空列表
  - 请求失败后停 100ms 再发下一个（成功的不停）：免得 503 这类毫秒级的失败让虚拟用户空转，把压测机自己打满。算吞吐时只数成功的请求

### 高性能系列的公共约定（实验 I–L）

高可用系列注入的是故障，高并发系列加的是量，高性能系列两样都不做：负载固定在一个远没压满的水平，看**一次请求本身**的时间和 CPU 花在哪，以及改一处之后变没变。所以有几条和前面不一样：

- **种子订单**：I、J、K 的查询查的是事先灌好的一批订单（mall-app 的 `POST /internal/demo/perf/seed`，各实验的 `run.ps1` 在压测前会确认灌过，没灌就灌，约 2 分钟）。4000 个普通用户各 200 单，另有 1 个大客户 20 万单，共 100 万单、200 万条明细；用户 ID 从 800000000 起，订单号是「8 + 6 位用户序号 + 6 位第几单」，压测脚本不查库就能拼出任意一单。一轮之内各个用户的订单交错着写，所以同一个用户的订单在主键上是散开的。订单状态是已取消，不会被关单、对账扫到。数据留在库里，各轮共用；`t_order` 约 500MB，比 MySQL 的缓冲池（128MB）大，这是有意的
- **整场的分位数**：`latency.csv`（每种请求整场的平均、P50 / P90 / P99 / P99.9 / P99.99 / 最大，微秒）。`timeline.csv` 是逐秒、整毫秒的，回答不了「平均快了 0.3ms 没有」
- **JVM 参数**：参数文件的 `[jvm]` 节按服务名给（`mall-app=-Xms1g -Xmx1g -XX:+UseZGC …`），不写就是 `-Xms512m -Xmx1g`；值里的 `{run}`、`{name}` 换成本轮结果目录和实例名
- **JFR**：`Start-HaJfr` / `Save-HaJfr`。录制要在流量进来之前开好，到点只取要看的那一段——带着流量开录制，那一刻要重新转换一批类、已编译的代码作废重编，试跑时下单的中位耗时从 30ms 涨到 4 秒，请求堆积后全场 504，约 50 秒才恢复
- **MySQL 语句统计**：批量驱动带 `-VmSsh` 时，I、J 会在要看的那一段开头清一次 `performance_schema` 的语句统计、结尾取回（`vm-mysql-digest.txt`：每类语句的次数、平均耗时、扫描行数、返回行数）。单独跑一轮时没有这份数据
- 汇总 JFR：`python experiments/tools/hp_jfr.py <xxx.jfr>`（CPU 采样与分配采样按线程类别、按库归类，网络读写按对端汇总；只依赖 JDK 自带的 `jfr` 命令）

### 实验 I：定位——一次请求的时间花在哪

- **假设**：不压到极限也能找出该改的地方。固定一个轻负载，先看数据库这一头（哪类语句最多、每次扫描多少行），再看应用这一头（CPU 采样落在哪一层），按占比从大到小改；每改一处都量得出变化，量不出变化的改动不值得做
- **前置条件**：同 A；种子订单已灌；20001–20003 都不在分桶状态
- **拓扑**：同 A（mall-app ×1）
- **压测**（`LocateSimulation`）：**开放**模型、固定速率——下单 50 单/秒（在 20001–20003 里随机挑，每个实验用户只下一单）、订单列表 200 次/秒（`GET /api/orders?size=20`）、订单详情 100 次/秒（`GET /api/orders/{orderNo}`），先预热 60 秒，再正式压 240 秒。两种查询在 4000 个种子用户里随机挑一个，列表查他最近 20 单，详情查他最近 20 单里的一单
  - 速率为什么这么低：试过翻一倍（100 / 300 / 200），放 MySQL 的 4 核虚拟机 CPU 到 70%，已经不算「远没压满」。现在这一档虚拟机 CPU 约 35%
  - demo 下订单 1 分钟后超时关单，所以压测期间后台一直有每秒 50 单在关（消费消息、调支付服务、释放预占），它们的 CPU 和数据库访问也在这台 mall-app 上——采样里「消息消费线程」「定时任务与 outbox」就是这部分
- **动作**（脚本做）：压测前在 mall-app、库存服务、网关上各开 JFR（锁等待与挂起的门槛降到 1ms，方法采样 5ms 一次；`i2-sockets` 另把每一次网络读写都记下来、不带调用栈）；第 80 秒清 MySQL 语句统计；第 290 秒取回语句统计、把这 210 秒的 JFR 写到 `jfr\`；压测后等实验订单关完

| 变体 | 订单列表的索引提示 | MySQL 驱动的连接属性 | 游标 | 服务的包 |
|------|------|------|------|------|
| `i1-baseline` | **不加**（修复之前的样子） | 默认 | JSON + Base64 | 当前 |
| `i2-index-hint`（正式代码） | 加 | 默认 | JSON + Base64 | 当前 |
| `i2-sockets` | 同 `i2-index-hint`，JFR 多记每一次网络读写（算 Tomcat 线程等 MySQL、等库存服务各多久；这几轮的方法采样少，CPU 归类不看它） | | | |
| `i2-jdk25` | 同 `i2-index-hint`，四个服务换 JDK 25 起（方法采样多 4–6 倍，用来核对 CPU 归类） | | | |
| `i3-jdbc-params` | 加 | **useLocalSessionState、cachePrepStmts 打开** | JSON + Base64 | 当前 |
| `i4-plain-cursor` | 加 | 默认 | **十进制字符串** | 当前 |
| `i0-before-port-fix` | 加 | 默认 | JSON + Base64 | **「管理端口每次都查配置」修复之前打的包** |

`i0-before-port-fix` 靠 `[script] jarDir` 指到另一个目录下的包：检出修复前的那次提交（见第九节）、打包、把四个 jar 拷进去。它和 `i2-index-hint` 只差这一处修改。

- **看哪些数据**：
  - 客户端：`latency.csv` 三种请求的平均、P50、P99、P99.9
  - 服务端：mall-app 三个接口的平均耗时、调库存预占的平均耗时与库存服务自己量的耗时（两者之差是网络与序列化）、网关量的总耗时与它调 mall-app 的耗时（两者之差是网关自己）
  - MySQL：`vm-mysql-digest.txt` 里次数最多、总耗时最多的语句，每类语句的「扫描行数 ÷ 返回行数」；会话状态类语句（`SELECT @@SESSION.…`、`SET …`）占全部语句的比例
  - JFR：`hp_jfr.py` 的 `cpu-by-layer.csv`（CPU 采样按层）、`alloc-by-layer.csv`、`socket-by-peer.csv`（Tomcat 线程等 MySQL、等库存服务各多久）
  - 资源：各服务进程 CPU、分配速率、GC 停顿；连接占用时长与每秒借出次数；虚拟机 CPU 与 iowait
- **预期**：这个实验的预期是在试跑里改过的——
  - 最初以为正式配置在这个负载下没有问题，实验只是量一量各层占比。第一次试跑就发现订单列表慢：语句统计里它每次扫描 221 行、只返回 21 行。`EXPLAIN` 显示 MySQL 选了下单幂等用的唯一索引 `uk_user_biz (user_id, biz_no)` 再排序，而不是 `idx_user_id (user_id, id)`；之前的实验里每个用户只有一两单，看不出来。修复是在 SQL 里加索引提示，`i1` 是加之前、`i2` 是加之后
  - `i2` 之后数据库这头剩下最显眼的是会话状态类语句，试跑里占全部语句的 46%：驱动每次写入前问一次是否只读、每次开关事务都发一次 `SET autocommit`。`i3` 用连接属性让驱动记住这些状态，预期语句数明显下降，下单耗时降一两毫秒
  - `i4` 预期和 `i2` 没有差别：微基准里十进制游标比 JSON + Base64 快几倍，但一次编码只有几十到一百多纳秒，放到毫秒级的请求里量不出来
  - 网关的 CPU 采样里约 7% 落在 `GatewaySecurityConfig.onManagementPort`：管理端口过滤链每个请求都判断一次「是不是打在管理端口上」，每次判断都去环境里查两个属性。修复是端口查到一次就记住；`i0` 是修复前的包，预期网关每个请求用的 CPU 比 `i2` 多几个百分点，耗时上未必量得出来
- **判定**：每个变体的三种请求各算服务端平均耗时与客户端 P50 / P99，变体之间比；`i3` 另比语句数，`i0` 另比网关的进程 CPU ÷ 每秒请求数。JFR 的方法采样在这台 Windows 开发机上每秒只有几个到十几个，同一变体的几轮合起来看，单轮里 1%–2% 的差别不算数
- **预计耗时**：每轮约 7 分钟——起服务 1 分钟、预热与压测 5 分钟、等关单 1 分钟

### 实验 J：数据访问——SQL 的几种写法各差多少

- **假设**：分页翻得越深，偏移量分页越慢，游标分页不受深度影响；一页订单逐单查明细（N+1）比一次查完慢一个量级；批量写入要同时满足「批量 API、驱动改写、事务分批」才快，缺一个就退回逐条的速度
- **前置条件**：同 A；种子订单已灌
- **拓扑**：同 A。请求直接打 mall-app 的 `/internal/demo/perf/**`（不经网关、不要登录）：比的是 SQL 的写法，不让网关和鉴权的耗时混进来。这些接口只在 demo profile 下注册（`mall-order` 的 `DemoPerfController`）
- **压测**（`DataAccessSimulation`，`ha.mode` 选三种之一）：
  - `deep-paging`：大客户（20 万单）的订单列表翻到第 0 / 1000 / 1 万 / 10 万 / 19 万行，每个深度用三种写法各压 20 秒（前 5 秒不计），4 个虚拟用户闭环。三种写法都用提示固定在 `idx_user_id` 上
  - `n-plus-one`：最近 20 单带明细，三种写法各压 60 秒（前 10 秒不计），16 个虚拟用户闭环，在前 100 个种子用户里随机挑
  - `batch-write`：1 个虚拟用户按顺序调，每次往 `t_order_item` 写 2 万行、返回服务端量的用时；每个用例写 3 遍（另有一遍 2000 行的预热）。写进去的行挂在一个不存在的订单上，量完删掉，删除不计时
- **动作**（脚本做）：压测一开始清 MySQL 语句统计，收尾时取回

| 变体 | 模式 | 对照的写法 |
|------|------|------|
| `j1-batch-write` | batch-write | 逐条自动提交；一个事务里逐条（每 1000 行提交）；一条语句多行（每批 10 / 100 / 1000 / 5000 行）；JDBC 批量（同样四种批大小）。驱动**不**改写批量语句 |
| `j1-batch-write-rewrite` | batch-write | 同上，连接属性加 `rewriteBatchedStatements=true` |
| `j2-deep-paging` | deep-paging | 偏移量（`LIMIT offset, 20`）；延迟关联（子查询先在索引上取这一页的主键，再回表）；游标（`id < 上一页最后一行`） |
| `j3-n-plus-one` | n-plus-one | 逐单查明细（1 + 20 条语句）；一次 `IN`（2 条）；一次 `JOIN`（1 条） |

- **看哪些数据**：`latency.csv` 每个用例的平均、P50、P99 与完成次数（闭环下次数就是吞吐）；`batch-write.csv` 每次调用的用时与每秒行数；`vm-mysql-digest.txt` 每类语句的次数与扫描行数（偏移量分页的扫描行数应当等于 offset + 20；JDBC 批量在改写前后发给 MySQL 的语句数差多少）
- **预期**：偏移量分页的耗时随深度线性增长，19 万行时以秒计（每一行都要回表，而表比缓冲池大）；延迟关联也随深度增长但斜率小得多（只扫索引）；游标是平的。N+1 的耗时约为一次查完的 5 倍以上。批量写：逐条每秒一两千行；JDBC 批量不改写时和逐条差不多（仍是一行一个往返）；一条语句多行与改写后的 JDBC 批量每秒几万行，批大小从 100 往上收益变小
- **判定**：每个用例取两轮的中位数；深分页画「深度 → 耗时」三条线
- **预计耗时**：`j1` 两个变体各约 4 分钟，`j2` 约 7 分钟，`j3` 约 5 分钟

### 实验 K：JVM——收集器、堆大小、预热

- **假设**：停顿不是 P99 的主要来源时，换收集器收益有限；它影响的是 P99.9 往后的尾部。ZGC 的停顿是亚毫秒，代价是并发回收多用 CPU。堆减半，回收次数翻倍，单次停顿变化不大。没有预热的实例直接接满流量，头几十秒的耗时比稳定时高一到两个量级
- **前置条件**：同 A；种子订单已灌；`k1-*-jdk25` 另要一个 JDK 25（环境变量 `MALL_JAVA25_HOME` 或 `-Java25Home`）
- **拓扑**：同 A，但压测**直接打 mall-app 的端口**（不经网关）：被测的只有 mall-app 的 JVM，而一次查询里网关那一跳比 mall-app 自己还久。mall-app 绑在 4 个逻辑 CPU 上（`[script] mallAppCpus=4`，JVM 参数同时加 `-XX:ActiveProcessorCount=4`），相当于一个 4 核的容器——开发机有 28 个逻辑 CPU，不限制的话并发回收的线程永远有空闲的核可用
- **压测**（`LocateSimulation`，不下单）：订单列表 1000 次/秒、订单详情 1000 次/秒，只读；在前 100 个种子用户里随机挑（让数据页留在 MySQL 的缓冲池里，磁盘读不混进来）。先预热 60 秒，再正式压 240 秒。`k2-cold`、`k2-ramp` 不预热，压 180 秒
- **动作**：无。GC 日志（`-Xlog:gc*,safepoint`）写到结果目录的 `gc-mall-app-1.log`

| 变体 | 收集器 | 堆 | JDK | 预热 |
|------|------|------|------|------|
| `k1-g1-1g` / `k1-g1-512m` | G1 | 1GB / 512MB | 21 | 60 秒 |
| `k1-zgc-1g` / `k1-zgc-512m` | 分代 ZGC（`-XX:+UseZGC -XX:+ZGenerational`） | 1GB / 512MB | 21 | 60 秒 |
| `k1-parallel-1g` / `k1-parallel-512m` | Parallel | 1GB / 512MB | 21 | 60 秒 |
| `k1-serial-1g` / `k1-serial-512m` | Serial | 1GB / 512MB | 21 | 60 秒 |
| `k1-g1-1g-jdk25` | G1 | 1GB | **25** | 60 秒 |
| `k1-zgc-1g-jdk25` | ZGC（JDK 24 起只有分代模式） | 1GB | **25** | 60 秒 |
| `k2-cold` | G1 | 1GB | 21 | **无**，第 0 秒就是全速 |
| `k2-ramp` | G1 | 1GB | 21 | **无**，开头 30 秒从 10% 线性升到 100% |
| `k2-c1-only` | G1，`-XX:TieredStopAtLevel=1`（只用 C1 编译器） | 1GB | 21 | 60 秒 |

- **看哪些数据**：`latency.csv` 的平均、P50、P99、P99.9、P99.99、最大；GC 日志里正式阶段的停顿次数、总时长、中位数、最长一次，以及全部安全点停顿（GC 之外的也算）；mall-app 的进程 CPU（4 核里用了几核）、分配速率；`k2` 另看 `timeline.csv` 头 60 秒逐秒的成功数与耗时
- **预期**：四种收集器的平均和 P50 差不多；P99.9 与最大值上 ZGC 最低、Serial 与 Parallel 最高；ZGC 的进程 CPU 比 G1 高。堆从 1GB 减到 512MB，回收次数约翻倍。`k2-cold` 头十几秒大量超时，之后恢复到和预热过的一样；`k2-ramp` 明显好于 `k2-cold`。`k2-c1-only` 稳定后的 CPU 高于默认
- **判定**：每个变体取两轮的中位数；两轮差得多的再补一轮
- **预计耗时**：`k1` 与 `k2-c1-only` 每轮约 6.5 分钟，`k2-cold`、`k2-ramp` 每轮约 4.5 分钟

### 实验 L：微基准——用 JMH 量几段纯 CPU 逻辑

- **假设**：手写计时循环量不准纯 CPU 的小段代码，JMH 能；量准之后会发现，这些小段代码里差几倍的写法，放回一次毫秒级的请求里大多看不出来
- **前置条件**：只要 JDK 21 和 Maven，不起服务、不连中间件；跑的时候机器上不要有别的重活
- **内容**（`bench` 模块，基准类和被测类放在相同的包名下，直接调包内可见的方法）：

| 基准 | 被测的代码 | 对照 |

| `OrderCursorBenchmark` | `OrderCursor` 的编码与解码（JSON + Base64 + 正则） | 游标直接用十进制字符串 |
| `BizExceptionBenchmark` | 在 1 / 30 / 120 层调用之下抛出 `BizException` 再接住 | 同样抛但不采集调用栈；不抛，逐层返回错误码 |
| `JwtDecodeBenchmark` | `SecurityConfig.jwtDecoder` 校验一个访问令牌，再转成登录用户 | — |
| `OrderViewJsonBenchmark` | 订单详情（1 单 2 条明细）、订单列表（20 单）从领域对象到视图、从视图到 JSON | — |
| `SnowflakeBenchmark` | `SnowflakeIdGenerator.nextId` | 1 个线程与 8 个线程 |
| `NaiveTimingDemo`（不是 JMH） | 同一个游标解码，手写 `System.nanoTime()` 循环 | 第 1 次、前 1000 次、预热后结果不用、预热后结果累加 |

- **判定**：两次完整的运行，得分取两次的平均，误差取 JMH 给的 99.9% 置信区间里较大的一个
- **预计耗时**：完整跑一遍约 8 分钟

## 七、安全与清理

- 故障注入、模拟 SIGTERM、降级开关，以及高并发系列的三个模型与缓存开关（`mall.demo.*`）都只在 demo profile 下存在，生产不注册；`prod` 与 `demo` 同时激活启动即失败
- 故障规则都有有效期（默认 10 分钟、最长 1 小时），脚本收尾时还会主动撤销；服务重启后规则全部消失
- 脚本只连本机服务和 `config/application-local.yml` 里的中间件，不连生产；内网地址只写在本地文件和命令行参数里，不进仓库
- 实验数据（订单、预占、本地消息）留在开发库里，想清空就在开发虚拟机上重建中间件的数据卷（需要先和共用这台机器的人确认）
- 实验 E 会把热点 SKU（20001）拆成桶，收尾时并回去；并不回去时脚本会在最后明说。分桶状态下补货接口不处理这个 SKU、下单走的是分桶那条路径，所以跑别的实验之前要确认它已经并回单行（做法见实验 E 的「动作」）
- 实验 F2 调的是运营后台的清缓存接口，令牌是用 dev 环境的本地占位 JWT 密钥签的 ADMIN 角色（和实验用户的令牌同一把密钥，只在本机的 dev / demo 环境有效）；它只清 20001 这一个 SKU 的缓存，不改任何数据
- 高性能系列的演示接口（`/internal/demo/perf/**`：灌种子订单、几种分页与批量写）和两个开关（`mall.demo.order-list.index-hint`、`mall.demo.order-list.plain-cursor`）同样只在 demo profile 下存在。种子订单（用户 ID 800000000 起）留在开发库的 `t_order`、`t_order_item` 里，共约 1GB，不想要了清空这两张表即可
- 实验 G 中途被打断时，没消费完的关单、释放消息留在 Broker 里，下一次起服务（不管跑哪个实验）会先把它们消费掉；G 自己在压测前会等它们消费完

## 八、局限

- 四个服务、压测、采样都在同一台机器上，CPU 互相抢；D 用容量模型规避，A、B、C 的绝对数值只对这台机器成立，看的是组间差异
- 中间件在虚拟机上，本机到虚拟机的网络延迟会计入每次数据库与 Redis 访问
- 实验用户不在 `t_user` 里，只覆盖只认令牌用户 ID 的接口
- Prometheus 5 秒一个点，秒级的细节以本机逐秒采样（`metrics.csv`）和 `timeline.csv` 为准
- 高并发系列的写入量比高可用系列大一个量级（每单在三个库里要提交七八次），开发虚拟机的磁盘先于代码成为瓶颈：试跑时每秒 50–150 单就多次出现库存库的写入整体卡住 1–9 秒（库存服务 40 条连接全部占着、预占成功数几秒不动，同一时刻 mall-app 自己的连接池没有积压，之后完全恢复），单行与分桶两种做法都有；原因没有在虚拟机上核实，按高可用系列记录过的「COMMIT 最长 6 秒」推测是磁盘刷盘停顿。E、H 的绝对数值只对这台虚拟机成立；停顿造成的失败和要测的拐点要分开看（见实验 E 的「判定」）。后来实验用的 MySQL 改成了不逐次刷盘（见「二、环境与拓扑」），`tools/run-batch.ps1` 每轮还会在虚拟机里起一个磁盘探针、核对本轮 COMMIT 的最大耗时，超过阈值就把这一轮标成 `CONTAMINATED.txt`
- 高并发系列的三个模型（E 的持锁 10ms、F2 的回源 200ms、G 的每条消息 100ms）都是为了把拐点放到一台开发机压得到的范围里、并且不随机器变化；它们决定了数字的大小，文章里引用这些数字时要连同模型一起交代。模型之外的部分（没有缓存时查库的拐点、下单接口的耗时）仍然只对这台机器成立
- 高性能系列的 JFR 方法采样在 Windows 上产出很低：JDK 21 上 1 个核在忙时每秒只有十几到二十个采样（按 5ms 一次算应该有两百个），同时记录全部网络读写时只剩三分之一；JDK 25 换了采样的实现，同样条件下多 4–6 倍。所以 CPU 归类看的是几轮合起来的比例，不看单轮里一两个百分点的差别；开了 JFR 的轮次只和同样开了 JFR 的轮次比耗时
- 实验 K 把 mall-app 绑在 4 个逻辑 CPU 上，但压测、网关、其余服务仍在同一台机器上自由调度，会和它抢这 4 个 CPU；客户端量到的 P99 在十几毫秒处有一个台阶，和这台机器的调度粒度有关，不全是 JVM 的事
- F 只有 3 个 SKU，缓存的键空间极小，看不到容量、淘汰、冷启动回填这些问题；单飞只在一个 JVM 内有效，本实验只起一个 mall-app，看不到多实例各回源一次
- E、H 的实验订单 1 分钟后关单是 demo 的节奏：关单（mall-app 的 order-timeout 消费者，每组 2 个线程）和释放预占（库存服务，和预占更新同一行或同一组桶）会和压测流量同时发生，相当于每单对库存行有两次更新。正式环境 15 分钟才关单、多数订单会支付，这一部分负载没有这么集中

## 九、实验结论与随后的修改

2026-11 跑完高可用系列的四个实验 A–D（每种做法 2 轮以上），文章在 Java Doc「高可用」模块的 12–15 篇。实验暴露的问题与对应的修改：

| 实验 | 发现 | 修改 |
|------|------|------|
| A | 服务间连接池是 HttpClient 5 的默认值（每个下游实例 5 条、取连接等 3 分钟），下游一慢调用全排在池子里，读超时不起作用 | 三个服务的 `application.yml`：`mall.http-client` 每实例 100 条、总数 200、取连接最多等 100ms |
| A、B | 舱壁包在熔断器里面，舱壁满抛的 `BulkheadFullException` 被熔断器记成成功，舱壁占满时熔断器打不开 | 三个熔断器实例加 `ignore-exceptions`（`application.yml` 与 `deploy/nacos/mall-app.yaml`） |
| C | 关掉 Nacos 自动注册后，停机时不会自动注销，不经过 preStop 的停机每次重启丢几百个请求 | `RegisterWhenReady` 在 `ContextClosedEvent` 最前面主动注销 |
| C | 注销后的等待（15 + 10 秒）短于调用方的实例缓存（35 秒） | LoadBalancer 实例缓存改成 5 秒（网关与三个服务） |
| C | 停机要 75–90 秒（消费者逐个关闭，每个约 30 秒），超过 60 秒宽限期 | `ParallelConsumerShutdown` 并行关闭消费者；Kubernetes 清单的宽限期改为 90 秒 |
| 跑实验时 | 启动瞬间连不上 Redis，应用启动失败但进程不退出 | 四个服务的 `main` 捕获启动异常后 `System.exit(1)` |
| D | 限流阈值 300/s 贴着容量（压满后实际处理约 316/s），一次积压就回不来 | `d2-limit`、`d4-limit-degrade` 的阈值改为 240/s |

2026-11-18 夜到 11-19 早上跑完高并发系列的四个实验 E–H（53 轮加 8 轮补跑，每个变体 2 轮以上），文章在 Java Doc「高并发」模块的 9–12 篇。这四个实验没有压出要改的正式配置，结论如下：

| 实验 | 结论 |
|------|------|
| E | 持锁 10ms 的模型下，单行 50 单/秒正常，100 单/秒时每秒只成功二十几单、之后稳定在约 11 单（排队超过 500ms 的读超时，超时的预占与补偿的 release 都是白做，熔断打开）；4、8、16 个桶最后一个全部成功的档位是 200、250、400 单/秒，过了拐点成功数停在平台上（4 个桶约 220、8 个桶约 280 单/秒），多出来的被舱壁拒绝。桶数翻倍容量不翻倍：持锁期间的 INSERT 与 COMMIT 随数据库变忙而变慢，16 个桶时库存服务的 40 条连接用到 39 条 |
| H | mall-app 的连接池 5、10、20、40、80：查订单列表吞吐约 2100、2560、2750、3180、3420 次/秒，下单成功率前三组 100%，40 时 39%–50%，80 时 22%–23%（查询把 4 核的数据库占到 91%，库存行锁等待累计从 132 秒涨到 5900 秒）。Tomcat 50 个线程吞吐低约 10%、P99 低三到四成；400 个线程因并发只有 200 没有比出差别。实例 1、2、3 个（并发同比例加）：查询吞吐只多 3%、10%，下单成功率 100%、43%、14% |
| F | 逐层对照到 4000 次/秒三种配置都没有拐点（主键查询太便宜；再往上压测工具先出问题），差别在数据库负载与 1–2ms 的耗时。击穿（回源 200ms、占着连接）：单飞每次失效回源 1 次，慢 0.2 秒；不单飞约 75 次，20 条连接分批跑，慢 0.7 秒。穿透：空值缓存把固定 100 个 ID 的查库从 3.6 万次降到 301 次，对随机 ID 无效，还占掉本机缓存 6000 条 |
| G | 下单接口在四个变体里没有差别（P99 14–27ms）。释放预占的消费组每条多停 100ms：8 个线程（约 75 条/秒）没有积压；4 个线程（37.4 条/秒）高峰消息最多晚 36.7 秒，高峰后约 80 秒追平；2 个线程（18.7 条/秒）低于平时的 20 条/秒，延迟一直涨到 3 分钟以上，停止下单约 4 分钟后才消化完 |

几点和预想不一样的地方，后面再跑时留意：

- 开发虚拟机上的 MySQL 即使不逐次刷盘，在每秒两三百单以上时仍会零星停顿（每轮 0–3 次，多数不到 1 秒，个别几秒，最长的两次 19 秒和 30 秒），所以 E 的 13 轮里有 8 轮带 `CONTAMINATED.txt`；停顿只影响当时那一级，同一级取多轮的中位数。MySQL 用的是默认的 128MB 缓冲池与 100MB redo，没有调
- F1 默认的阶梯（到 1600 次/秒）压不出任何差别；用 `-Set` 把阶梯改成 2000–4000 次/秒可以再往上看一段，到 5000 次/秒时 Gatling 报大量 `Connection refused` 随后内存溢出，是压测工具的上限
- H 的 400 线程变体要把 `ha.users` 加到 400 以上才有意义
- 53 轮里有 6 次服务没起来：5 次是 mall-app 启动瞬间连 Redis 超时（200ms），进程直接退出；1 次是上一轮的库存服务没退干净、管理端口还占着（`run-batch.ps1` 的清理原先只看服务端口，已补上管理端口）。批量驱动都重跑了一次；补跑的 8 轮之外另有 1 次库存服务启动失败，同样重跑通过
